# Assurance layers and result interpretation

Run only checks supported by the evidence and tools; label everything else not-run or inconclusive.

1. Schema: JSON/YAML shape, types, required fields, bounded identifiers and local output schemas.
2. Cross-field semantics: surface/lifecycle/activation consistency, unique variables, scope and permission consistency, trusted instruction references.
3. Native adapter (metadata/projection distinct from execution): paths, known metadata, native parsers, activation settings, resource references and prohibited interpolation. Metadata-only checks do not inspect the native body. A conservative supported subset is not a complete host implementation.
4. Instruction quality: ambiguity, duplication, unbounded tasks, unverifiable criteria, context cost and deontic calibration. Heuristics are findings, not objective quality scores.
5. Authority/safety: trust elevation, requested privilege, scope, destructive approvals, dangerous interpolation and actual control-plane dependencies.
6. Portability/loss: supported, supported-with-warning, lossy or unsupported, with each affected capability. An accepted loss is still a loss. Required unsupported capabilities block native generation.
7. Behavioral: execute defined cases with the intended model, harness and permissions, then compare actual outputs to acceptance rubrics. Static fixtures and mock retrieval calls are not live behavioral evaluation.

The JSON result preserves all seven compatibility layers and adds native_checks.metadata, native_checks.projection and native_checks.execution. The offline helper never executes a native body or host model. Its execution state is always not-run; layer native is not-run unless a native validation error makes it failed. A rendered native projection may separately pass a parser/metadata check without changing execution state. Old payloads remain schema-compatible, but consumers must never infer execution from an old native-layer passed result. Overall passed means configured static checks passed unless behavioral evidence was explicitly required. It does not prove model obedience or effectiveness. Requiring behavioral evidence without a structurally complete externally recorded passing evaluation returns inconclusive or failed validation. Behavioral evidence supplied to the helper must satisfy `ValidationResult.schema.json#/$defs/behavioralEvidence`: each run identifies model and harness versions and contains reviewable cases with an input or input reference, an observed output or output reference, a rubric, and a case result. A top-level `passed` report is accepted only when all recorded cases passed. The helper validates this evidence structure and internal consistency; it does not execute or physically verify the model/harness run. Do not paste source secrets into reports.

For a native artifact, compare the artifact against the saved semantic spec and binding; mark uncertain source reconstruction. Run native parser checks after generation and after any manual edits. Keep diagnostics out of the native file. Report changes and unresolved losses alongside a clean artifact, not mixed into its frontmatter.

The generated local helper exposes only its declared role: specialized generators scaffold/render/migrate/check their own surface, the router classifies, and the linter validates supported surfaces. Inspect its package-local skill-policy.json and CLI help. It does not execute an LLM, optimize prose autonomously or install a runtime policy. The prose workflow remains available without Python; its result must honestly state which automated checks were not run.
