# Persistent rules

Keep transient task payloads and session status out of persistent rules.

## Establish applicability

Inspect the authorized instruction files, project structure, actual consumers, and applicable standards. Determine discovery, directory or path scope, precedence, overrides, and any configured filenames before choosing placement. A nearby file does not necessarily override its parents, and applicability does not grant access.

Keep rules that affect execution: project purpose, verified commands, material conventions, permission boundaries, secret handling, exclusions, and completion criteria. Derive commands from actual configuration or CI. Do not install instruction files or run embedded commands unless authorized.

## Preserve rules during consolidation

Before moving or merging content, track each material source rule in working notes: retained, moved, merged with an equivalent rule, or removed with evidence or explicit authorization. Preserve restrictions, exceptions, non-goals, authority, and scope. Keep unresolved contradictions visible rather than guessing a policy decision.

Merge duplicates only when meaning, strength, and applicability match. A rule limited to one subtree must not become workspace-wide accidentally. Retain material safety rules even if they seem obvious. Remove stale claims only on evidence or within an explicitly authorized change.

Distinguish structural consolidation from semantic improvement. If both are requested, separate organizational moves from changes to behavior and compare the result against the preserved requirements.

For example, parent guidance requires checks before merge; child guidance permits skipping image checks for text-only changes under that child. Preserve the parent's merge gate and the child's conditional exception at its original scope. Do not widen that exception to the workspace or remove it as a duplicate. If a parent explicitly forbids exceptions while a child permits one, retain the conflict for disposition unless verified host precedence resolves it. A target unable to represent the required path scope or precedence blocks faithful migration.

## Write and verify the result

Apply the entrypoint's native checks to actual discovery, activation, and precedence. Do not invent required frontmatter for a plain instruction file.

Link substantial detail only at verified paths and explain when to read it. Keep universal rules close to the entrypoint and scoped exceptions near their affected work. Do not impose a file count or line quota.

For migration, compare discovery, scope, precedence, and authority before finalizing. Surface required unsupported behavior as a blocker; identify optional losses for explicit acceptance.

Return the clean instruction file or files. For edits, briefly account for material moves, merges, removals, or unresolved conflicts outside the artifact; a separate ledger file is unnecessary unless requested. Check semantic coverage, scope, references, and native syntax where applicable. Distinguish static checks from observed host loading and model behavior.
