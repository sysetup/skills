## Device selection

| Device | Use it to | Keep it honest by |
| --- | --- | --- |
| Analogy | Explain a relationship through a different familiar system | Mapping the important parts and naming a relevant difference |
| Similarity or simile | Highlight one shared feature, often using "like" or "as" | Restricting the claim to that feature |
| Metaphor | Give a vivid first image, such as "a bottleneck" | Translating the image into its literal meaning |
| Figurative mini-story | Make a sequence or interaction visible | Marking it as imagined and returning to real events |
| Concrete example | Show an actual instance of the concept | Labeling hypothetical cases and preserving real rules |
| Counterexample | Prevent an overgeneralization | Identifying exactly which condition changed |

Use one or two devices as needed. Do not combine every device in every answer. Favor a concrete example when a metaphor would obscure an exact definition.

## Structural mapping

Construct a small private mapping before drafting:

| Element | Question |
| --- | --- |
| Target | What real concept or situation needs explaining? |
| Source | What familiar scene has the same useful relationship? |
| Correspondences | Which two to four parts or actions match? |
| Mechanism | What change in the source resembles what change in the target? |
| Boundary | Which inference would become false outside that shared relationship? |
| Application | What can the user understand or decide after the comparison? |

Choose relationships over appearances. A queue can explain waiting under limited capacity because both involve arrivals and service. A blue object does not explain another blue object's function merely because the colors match.

Avoid chained comparisons in which the source itself needs another analogy. Avoid switching scenes halfway through an explanation. If a second analogy adds a different insight, complete the first, state the new purpose, and keep their mappings separate.

Use the domain examples below only where their structure fits:

| Topic family | Possible source scene | Useful relationship | Likely boundary |
| --- | --- | --- | --- |
| Capacity and delay | A queue at a narrow entrance | Arrival rate, service rate, waiting | Real systems may have parallel paths and variable service times |
| Dependencies | Tasks that need earlier tasks completed | Order and prerequisite failure | Some dependencies can be removed or handled in parallel |
| Error checking | Comparing a copied list with its original | Detecting mismatches | A particular check may miss some kinds of errors |
| Permissions | Different keys for different doors | Limited access for specific roles | Digital permissions can be copied or inherited differently |
| Tradeoffs | Space in a container | One choice uses a limited resource | Some improvements create new capacity rather than redistribute it |
| Abstract categories | Objects grouped by a stated rule | Membership and exceptions | The grouping rule, not appearance, determines membership |

For a topic outside these families, derive a new mapping instead of forcing one from the table.

## Concepts and explanations

Use this optional prose scaffold:

> [Literal main idea.] Imagine [familiar scene]. [Source element] plays the role of [target element], and [source action] resembles [target action]. For example, [small concrete event]. The comparison works for [shared relationship], but [important difference]. In the real topic, this means [takeaway].

For age-11, combine this into a few short sentences and keep only the key roles. For a technical adult audience, retain exact terminology and use the image to support it.

## Problems and uncertainty

Use a comparison to organize observations, not to turn a guess into a diagnosis.

1. State what the user has actually observed.
2. Explain one plausible mechanism through the scene.
3. State what evidence would support or weaken that mechanism.
4. Give a justified next check or ask for essential missing information.
5. Clarify where the scene differs from the real problem.

Example shape: "A slow service can resemble a queue with one slow station. That suggests checking where waiting builds up. It does not establish that a particular component is the cause."

When several causes remain plausible, keep the image neutral and compare the causes in literal terms. Do not prescribe a change simply because it solves the imagined story.

## Proposals and comparisons

For a proposal, explain the current process, proposed change, expected benefit, cost, and required conditions. Use tentative language for predictions and preserve evidence separately from the comparison.

Optional structure:

> The current process resembles [scene]. The proposal changes [mapped part]. That could improve [outcome] if [condition]. It may also create [tradeoff]. The story leaves out [real-world constraint], so assess the proposal using [actual criterion or evidence].

For competing proposals, keep a common source scene and a common set of criteria. Do not make one option a heroic character and the other a foolish character. Translate persuasive imagery back into measurable or inspectable claims.

If the user requests a recommendation, base it on stated goals and evidence. A neat analogy can explain the recommendation but cannot justify it by itself.

## Procedures

Explain the purpose through an analogy, then switch to literal steps. Do not replace executable details with figurative commands.

- Keep exact filenames, commands, settings, quantities, units, and order unchanged when they are required.
- Identify prerequisites and irreversible steps when relevant.
- Use placeholders only when clearly marked; do not imply that a fictional example has been executed.
- Add the comparison around the steps rather than inside syntax that must be copied exactly.

For example, calling a backup "a spare copy" may explain why it helps; it does not tell the user which files were backed up or prove that restoration works.

## Figurative stories and emotions

Introduce an imagined scene explicitly. Give nonhuman things temporary roles only if the user can distinguish the story from the mechanism. Avoid implying that software, cells, markets, or nature have human goals or feelings unless discussing those attributions as metaphor.

For emotional topics, use gentle optional comparisons grounded in what the user has said. Do not use a story to label someone as broken, malicious, weak, or disordered. Do not claim to know another person's motives. If the image does not fit the user's experience, abandon it rather than defend it.

For polarizing or contested issues, attribute viewpoints and uncertainties in literal terms. Avoid loading the comparison with an unsupported moral conclusion.

## Quantities and exact details

- Mark invented numbers as hypothetical before using them.
- Keep quantities and units consistent between the scenario and the real explanation.
- State assumptions before a calculation and interpret the result afterward.
- Avoid comparing quantities with different denominators or silently changing time periods.
- Preserve distinctions such as correlation versus causation, probability versus certainty, and a rate versus a total.
- If an analogy cannot preserve an essential condition, stop using it for that condition and explain it literally.

Do not use numerical detail merely to distinguish adult modes. Add it only when it clarifies the subject or the requested decision.

## Repair and concise formats

For "I still do not understand," change the source scene or isolate one relationship. For "That comparison is wrong," acknowledge the material mismatch, correct the literal claim if needed, and choose a better model. Do not hide a factual correction inside a new metaphor.

For a one-sentence request, compress the essential mapping and boundary: "[Target] is like [source] because [relationship], though [important difference]." Add the literal term within the sentence when possible.

For a requested story-only format, keep the scene plainly fictional and make the intended mapping and material limit understandable within the requested format. If precision or urgent safety requires a literal statement, provide it rather than preserve a misleading constraint.

For "No analogies," stop using this style. For another language, adapt the scene and wording naturally instead of translating an idiom word for word.
