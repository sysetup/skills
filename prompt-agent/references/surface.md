# Agent definitions and privileged intent

Define stable responsibility, decision boundaries, tool envelope, escalation and output expectations. Do not invent credentials, capabilities or maximum autonomy. An agent definition is a durable behavior/configuration object, not every individual request sent to an agent.

Record authority as semantic intent. Consult the adapter for native agent metadata or privileged instruction placement. A host may not expose a literal system prompt; unsupported agent configuration must be reported, not manufactured by adding a heading or arbitrary frontmatter.

Inspect tool inheritance carefully. Omitted native tools may inherit a parent's tools; a prompt-level deny instruction is not a sandbox. Map explicit tool permissions only to verified installed tool names and host controls. Do not broaden user authorization while migrating. List approval-required actions and how the agent handles inadequate permission.

Keep user documents, retrieved content and transient arguments outside the privileged definition. Define their trust boundaries and handling rules rather than concatenating them into the agent's instructions. Prevent conflicts with parent or host policy; do not claim the agent outranks the host.

Completion: return a native definition where supported, tool/permission mapping, known inheritance and authority limitations, and separate validation evidence. A generic privileged-instruction draft remains a draft requiring a consumer; it is not an installed agent.
